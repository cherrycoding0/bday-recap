## A. 참여 퍼널 측정 — "숫자를 만드는 기능" (예상: 반나절)

### 목적
생일이 지난 뒤 "방문 N명 → 테스트 완료율 N% → 메시지 전환율 N%"라는
**실측 문장**을 이력서에 쓰기 위함. 기능이 아니라 증거를 만드는 작업.

### DB
```sql
create table events (
  id uuid primary key default gen_random_uuid(),
  session_id text not null,   -- 브라우저별 익명 ID (개인정보 아님)
  event text not null,        -- 아래 이벤트명 중 하나
  meta jsonb,                 -- 예: { "type": "allcon" }
  created_at timestamptz default now()
);
-- RLS: 익명은 insert만 가능. select는 관리자(admins)만 → 데이터 유출 없음
```

### 수집 이벤트 (7종)
| 이벤트 | 시점 | meta |
|---|---|---|
| `visit` | 페이지 첫 로드 (세션당 1회) | - |
| `quiz_start` | 테스트 시작하기 클릭 | - |
| `quiz_complete` | 결과 도달 | 유형 id |
| `message_posted` | 메시지 저장 성공 | 경로(퀴즈폼/일반폼) |
| `card_saved` | 카드 이미지 저장 클릭 | 유형 id |
| `share_clicked` | 자랑하기 클릭 | - |
| `fancam_clicked` | 직캠 보러가기 클릭 | 곡명 |

### 구현
- `lib/track.ts`: `track("quiz_start")` 한 줄로 쓰는 fire-and-forget 함수.
  session_id는 localStorage의 randomUUID (없으면 생성). 실패해도 조용히 무시 — 추적이 UX를 못 막게.
- 각 컴포넌트에 track() 호출 7곳 추가 (침습 최소)

### 대시보드 `/stats` (관리자 전용)
- 관리자 로그인 시에만 데이터 조회 가능 (RLS select 정책)
- 표시: 단계별 인원수 퍼널 바 / 단계간 전환율 / 일별 추이 / 유형 분포(D와 공유)

### 이력서 문장 (생일 후 실측치로 채움)
> "이벤트 퍼널을 설계·수집하여 방문→참여 전환율 N%를 측정, 병목 단계를 식별"

## B. 실시간 롤링페이퍼 (예상: 반나절)

### 목적
다른 팬의 메시지가 **새로고침 없이** 화면에 나타남. WebSocket/실시간 동기화 경력 키워드.
D-day 자정에 메시지가 실시간으로 쏟아지는 연출과 결합하면 극적.

### 구현
- Supabase Realtime 사용 — 인프라 추가 없음. SQL 한 줄로 활성화:
  `alter publication supabase_realtime add table messages;`
- `RollingPaper`에서 채널 구독:
  - INSERT 이벤트 → 목록 맨 앞에 추가 + 보라색 하이라이트 페이드 애니메이션
  - DELETE 이벤트 → 목록에서 제거 (관리자 삭제도 모두에게 실시간 반영)
- 904 카운터·띠배너도 같은 구독을 공유해 폴링(60초/120초) 제거 → 오히려 요청 수 감소
- 엣지 케이스: 내가 방금 쓴 메시지가 낙관적 업데이트 + 실시간 이벤트로 중복 표시되지 않게 id dedupe

### 이력서 문장
> "Supabase Realtime(WebSocket) 기반 실시간 롤링페이퍼 구현, 폴링 제거로 요청 수 절감"

## C. AI 모더레이션 2차 심사 (예상: 반나절)

### 목적
1차 단어 필터의 한계(우회·오탐) 를 LLM 맥락 판정으로 보완.
리캡(요약)·코멘트(생성)·모더레이션(판정) — **LLM 활용 3종 세트 완성**.

### 흐름
```
메시지 제출
 ├─ 1차 필터 '확실한 차단' (욕설 직격 등) → 즉시 거부 (현행, 비용 0)
 ├─ 1차 필터 '애매' (신규 카테고리: 우회 의심 패턴 등) → /api/moderate 로 LLM 판정
 │    ├─ 허용 → 저장
 │    └─ 거부 → 사유와 함께 반려
 └─ 통과 → 즉시 저장 (현행, 비용 0)
```
### 설계 포인트
- **비용**: LLM은 '애매' 케이스에만 호출 (전체의 수 % 예상) + Haiku급 + IP 레이트리밋
- **폴백**: API 실패/키 없음 시 보수적으로 거부 (생일 축하 페이지 특성상 안전 우선)
- **감사 로그**: 판정 결과를 events 테이블(meta)에 남겨 오판율 사후 분석 → 이것도 포폴 소재
- (선택) messages에 `hidden` 플래그 + 관리자 '숨김' 토글 — 삭제보다 온건한 운영 수단

### 이력서 문장
> "규칙 기반 1차 + LLM 2차 하이브리드 모더레이션 파이프라인 설계, LLM 호출을 의심 케이스로 한정해 비용 최적화"

## D. 유형 통계 (예상: 2시간, A 위에 얹으면)

### 목적
결과 화면에 "당신 같은 눈물샘형은 전체의 12%예요" — 희소성/공감 재미로 공유 욕구 강화.

### 구현
- A의 `quiz_complete` 이벤트(meta.type)를 그대로 집계 — **별도 테이블 불필요**
- `/api/type-stats`: 유형별 카운트 집계 (5분 캐시 — 리캡과 같은 패턴)
- 결과 화면에 한 줄 + 얇은 분포 바. 표본이 적을 땐(예: 30명 미만) 숨김 처리 — "0%" 민망함 방지
